# performance-measurement/v1

Each benchmark process returns exit 0 and one JSON object. It may first emit the
configured readiness marker followed by a newline and flush it. No other stdout.
Human diagnostics go to stderr; DEBUG BUILD banners are refused. Commands are
non-secret argv arrays, not shell strings. Arbitrary executable benchmarks have
the caller's authority: this tool is not a sandbox for untrusted commands.

```json
{
  "schema": "performance-measurement/v1",
  "correct": true,
  "build_mode": "ReleaseFast",
  "allocator_coverage": "tracked native allocator for decoder state",
  "rows": [
    {"size": 1024, "samples": {"cpu_ns": [1200,1210,1190], "wall_ns": [1300,1305,1290], "peak_bytes": [2048,2048,2048]}, "residual_bytes": [0,0,0]},
    {"size": 2048, "samples": {"cpu_ns": [2400,2410,2390], "wall_ns": [2600,2605,2590], "peak_bytes": [4096,4096,4096]}, "residual_bytes": [0,0,0]}
  ]
}
```

Every configured size must be present in order. Each selected metric has at least
three positive finite samples in its documented units. `cpu_ns` is process/thread
CPU duration, `wall_ns` monotonic elapsed duration; describe the actual clock and
batched iteration normalization in extra metadata. Counts/byte metrics are
requested units, never converted to fictitious timing. Zero-denominator growth
is invalid; use a defined resource/absolute contract for a zero-sized metric.

`correct: true` is an adapter's claim, not sufficient independent evidence by
itself. Its tests must demonstrate the work oracle fails on wrong/skipped work.
The engine cannot prove the honesty of arbitrary benchmark code or history writers.
Nix pins the implementation; external immutable records protect accidental
overwrite, not an adversary with directory write access.

For `mode: "mg"`, include allocator coverage and at least three residual values
after complete cleanup cycles at each size. These nonnegative values are checked
against the configured allowance, independently of historical ratios. Include
additional live/allocation/reallocation records where the adapter supports them.

`metric: "startup_ns"` is generated by the runner from five spawn-to-ready
durations and needs `comparison: "absolute"`, one size, and a readiness marker.
The command's actual work still must verify. Other startup intervals should be
explicitly labeled supplemental data, never silently substituted for full startup.

All returned diagnostic fields are retained in the raw measurement. Only the
configured metric influences that case's historical comparison. Use distinct
cases to gate CPU, wall or multiple memory metrics separately. They can share one
adapter; a future persistent adapter can avoid repeated warmup without changing
evaluation policy.
